# Design to Test

The four stages a change passes through, and what may not happen until the stage before it
has an artefact.

**On release 0.0.2.** Written after an evening in which seven UI slices were planned with no
design, and the design file was then written by reading the code it was meant to judge.

## Why

Every failure of the dashboard work this week has the same shape: **the thing that decides
whether the work is right was produced by the work itself.**

`packages/tui/config/design.yaml` was authored by a task that read `screens.tsx` and wrote
down what it already drew. `the-cockpit-matches-its-design` then passed 63 of 63 against a
board that looked nothing like the signed-off proposal. Nothing was broken; the gate was
comparing the code to itself.

The state machine already refuses work with no test. It has nothing to say about work with
no design.

## The four stages

| stage | artefact | decided by | gate before the next stage |
|---|---|---|---|
| **design** | a `design` row, and the file it governs | you accept it | every component it touches exists; every claim it uses is approved |
| **plan** | criteria, acceptance artefact, tasks with scopes | the planner | the artefact is **red at base** *and* the story's design is accepted |
| **build** | commits on a task branch | the agent | the branch holds a commit that is neither the base nor a refresh |
| **test** | the acceptance test, judged by the design's reader | the gate | the reader reports no divergence |

Three of those four gates exist. The missing one is *plan requires an accepted design*.

## A design names the port it crosses, and the port names the reader

`crosses` is already in the design entity (page 20) and unbuilt. It is what makes a design
typed rather than filed-by-convention: today `design.yaml` is a UI design only because of
which directory it sits in.

| crosses | reader | how it judges |
|---|---|---|
| `!ui` | **wecode-lens** | `expected(design)` → capture the screen → `diff` and `check`; reports gone, arrived, moved, changed |
| structure (no port) | **the explorer's reflexion model** | model + map + source → convergence, divergence, absence |
| `!db` | the schema shapes test | the table set the code believes in |
| none of these | the named acceptance test alone | it is an ordinary change |

The reader is selected by the record, not chosen by whoever writes the test. That is the
difference between a design that is checked and a design that is filed.

## Why the design must be red first

A design accepted while its gate is green is a transcript of the code.

So `accept` on a design whose reader reports **no divergence at the base** is refused, in
the same words and for the same reason a test that has never failed cannot pass: it may be
asserting what the code already does. The screen the operator signed off is, by
construction, not the screen that is drawn yet.

## The designer

Any story whose design crosses `!ui` is not planned by hand from a picture in somebody's head:
it dispatches a **designer** — an agent in the `designer` role — who opens a painter session
(`wecode paint`) on a mockup and designs it *with* the operator until it is signed.

| from | the designer's first move | then |
|---|---|---|
| a blank page | **options**: two or three layouts and colour schemes side by side, each a real page, none of them the answer yet | the operator picks one; layout next, then detail |
| an existing screen | the current screen captured beside the proposed change, the difference marked | detail |

| step | artefact | ends when |
|---|---|---|
| options | `packages/<package>/design/<story-slug>.options.html` | the operator marks one |
| layout | `…/<story-slug>.html` — structure, no data, no polish | the operator's marks on the session are all answered |
| detail | the same file, finished: real content, states, empty cases | the operator signs it in NEEDS YOU |
| declaration | `design.yaml` `renderers.<renderer>` names the pages and blocks the mockup shows | the plan gate reads it |

The mockup is the design; HTML, CSS and JS are the design tool. The designer's marks arrive
through the painter session — element picks, text ranges, notes — and the right pane of that
session is the designer's own terminal, so a mark is answered by editing the file, not by
talking about it. The sign-off is an approval row like any other; the drawing is not planned
until it is answered. Divergence between the served page and the signed mockup is the lens's
to report: capture(mockup) against capture(served), structure compared, data masked.

The designer writes only under `packages/*/design/**` and the renderer blocks of `design.yaml`.
It never touches `src/`: what it produces is the thing the engineer's task is gated against.

### Painter and lens

Two components, one boundary: **painter carries intent in, lens reads the result out.**

| | `@wecode/painter` | `@wecode/lens` |
|---|---|---|
| is | the studio: serves an artefact, takes the operator's marks, holds the sign-off, hosts the designer's terminal | the judge: captures a screen, derives `expected()` from the design, reports gone / arrived / moved / changed, checks the four rules |
| input | a person, live | a design and a built page, unattended |
| output | marks and an approval row | a verdict |
| depends on | lens — for reading a page through CDP and for the layout check it shows the designer | core only; never painter |

Where they meet: the layout warnings a painter session shows are lens's `check` run on the
mockup, not a second audit; and the mockup painter signs is the file lens's `expected()` reads
for the webapp renderer, so capture(mockup) and capture(served) are compared by the same code
that judges the terminal. Painter never judges; lens never talks to a person.

## What needs your signature

| | |
|---|---|
| a design that crosses a port, or asks for a library | **you** |
| a design inside one component, crossing nothing | the gate |
| the reader's verdict | never a person — it is computed, and a changed verdict is level 5 |

Signing every design would mean signing a dashboard tweak at two in the morning; signing
none would mean a boundary moves without you. The port is the line between them.

## Invariants

| | |
|---|---|
| a story in `ready` or beyond has exactly one accepted design |
| a design is accepted only after its reader has reported divergence at the base |
| every design that crosses `!ui` governs a file some screen is captured against |
| the reader a design is judged by is read from `crosses`, never named in the test |
| a design is never authored from the tree it will judge |

## What this is not

| | |
|---|---|
| **not a second planner.** The plan file is unchanged; it gains one refusal |
| **not a document review step.** Nothing waits on prose being nice; `accept` asks the reader |
| **not a UI feature.** `!ui` is one row in the reader table |

## Leans on

Parnas — a boundary is authored, not discovered. Murphy, Notkin & Sullivan, *Software
Reflexion Models* — a model, a map, and a source, compared. And the oldest rule in this
repository: the gate is the judge, so the thing it judges against may not be written by the
thing being judged.

## The plan gate, if a planner ever writes plans

A planner seat is recorded and not built (story #444). The risk is not that an agent plans
badly — the gate catches that — it is that a plausible plan reaches the operator with
nothing checked, and approving it becomes rubber-stamping. So a plan an agent wrote is
**held** and may only be offered for approval once every one of these has passed. None of
them is a judgement; each is a check a machine runs and reports.

| # | the check | why it is not judgement |
|---|---|---|
| 1 | every file in every scope exists, or the task declares it as added | `ls` |
| 2 | no two tasks in the plan share a write path | set intersection |
| 3 | every scope lies inside one component of the map | the map is data |
| 4 | the acceptance artefact is a path the plan creates or that exists | `ls` |
| 5 | the artefact is **red at the base**, watched and recorded | the examiner ran it |
| 6 | no file named in any gate is in the doctor's red-at-base list | the list is a row |
| 7 | every gate file that exists passes at the base | the examiner ran it |
| 8 | the task's own test names the artefact it is judged by | string equality |
| 9 | no scope file is over the ceiling, or the task's title says it splits one | `wc -l` |
| 10 | the story has an accepted design, or crosses nothing and touches one component | the record |

A plan that fails any of them is returned to the planner with the failing number, and never
reaches a person. A plan that passes all ten is raised as one approval row in **needs you**,
carrying the ten green checks and the diff of what it would create — so the operator is
approving *intent*, having been told mechanically that the shape is sound.

**The operator's yes is still required.** Ten green checks say the plan is well formed, not
that it is worth doing; that is the one part no gate can compute.
