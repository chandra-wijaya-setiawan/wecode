# Mapping an Existing Repo

Giving a repository a structure it never had, without moving a file.

**On release 0.0.5.** Not started; drawn before implementation so it is not invented twice.

## Why

Every gate wecode owns assumes a repository built under it. `components-cover-the-tree`
wants every module owned on day one. A task scope is an exact file list, decided before
anyone has read the code. Red-at-base wants a named test file per criteria. A repository of
any age fails all three before its first story, and onboarding asks for the map rather than
working it out.

So wecode today can build itself and cannot be adopted. That is the whole product risk.

## The idea: the map is a third artefact

Not two files — three.

| | holds | authored by | changes when |
|---|---|---|---|
| **the model** | the structure you intend: containers, components, layers, what may reach what | you, once | the design changes |
| **the map** | which real paths and symbols belong to which node of the model | derived, then corrected | the tree moves |
| **the source** | `file.py`, `script.ts`, wherever they actually sit | everyone, daily | constantly |

The model never mentions a path. The source never mentions the model. **The map is the only
place the two meet**, which is what lets a repository keep its own layout while wecode
reasons in its own vocabulary.

```yaml
# architecture.yaml — the model: nothing here is a path
containers:
  - id: api            crosses: [!db, !http]
  - id: worker         crosses: [!db, !queue]
  - id: shared
components:
  - { id: api/billing,  in: api }
  - { id: api/identity, in: api }
  - { id: shared/money, in: shared }
forbidden:
  - { from: shared, to: api }     # a library may not reach its caller

# map.yaml — the only file that knows where anything lives
api/billing:
  - "src/handlers/invoice*.py"
  - "src/services/charge.py"
  - symbol: "BillingService"      # by symbol, when paths lie
shared/money:
  - "lib/money/**"
  - "vendor/currency_tables.py"
```

**A node may be scattered.** `api/billing` can be four files in three directories and one
class inside a god-module. That is the point: the abstraction is bounded by meaning, not by
folder. A repository that grew for ten years has its structure smeared across the tree, and
the map is where you say so.

## Three verdicts, not one

The reflexion triple, which is what makes this a check rather than a drawing:

| verdict | means | what wecode does |
|---|---|---|
| **convergence** | the model says these may talk, and they do | nothing; this is the repo working |
| **divergence** | an edge exists in the source that the model forbids | a violation the doctor reports, with both files named |
| **absence** | the model expects an edge that is not there | usually the model is stale, or the work is unbuilt |

A fourth state matters more for adoption than any of them: **unmapped**. Every file the map
does not claim. Day one that is 95% of the tree, and that is fine — see the ratchet.

## The explorer's task: derive the first draft

A person will not hand-write a map for 5,000 files, so the explorer proposes one and the
person corrects it. This is architecture recovery, and it is well trodden: cluster modules
by their inter-dependencies to suggest a gross decomposition, the technique behind Lattix's
dependency structure matrices, Sonargraph, Understand and Titan.

| signal the explorer already has | what it suggests |
|---|---|
| import edges between modules | clusters — a group that imports itself far more than its neighbours |
| directory names | a first guess at node names, discarded when the imports disagree |
| symbols a module exports and who takes them up | the seam between two candidate components |
| test files and what they import | the feature boundary, often truer than the source layout |
| the manifest | external libraries, which are stack claims rather than nodes |

The output is a **proposal, never a fact**. It arrives as work that needs a person: *here
are nine clusters, here is the name I would give each, here are the 340 files I could not
place.* Naming is judgement and stays yours.

## The ratchet is what makes day one possible

The mistake would be to demand a complete map before the first story. Instead measure
coverage and refuse a change that lowers it, exactly as `.max-lines` was ratcheted.

| | day one | after a month |
|---|---|---|
| mapped modules | 12% | 40% |
| the gate | *no change may lower 12%* | *no change may lower 40%* |
| a task touching unmapped files | allowed, and asked to map them | rarer |

So the map grows with the work rather than blocking it, and the first story ships on day
one instead of after a mapping project nobody funds.

## What this changes elsewhere

| | |
|---|---|
| **scope** | a task's scope is a *node*, resolved through the map to files at dispatch — so a scope survives a file move, and an agent is told the boundary in the model's words |
| **the component map** | `components.yaml` becomes the wecode project's own instance of `architecture.yaml` plus a map that is trivially the directory layout |
| **the doctor** | gains divergence as a violation kind, with the two files that prove it |
| **the explorer** | gains a verb: propose a map, and report the three verdicts against one |
| **the design entity** | a design's `touches` names nodes, which is why they had to be addressable |

## What this is not

| | |
|---|---|
| **not a refactor.** Nothing moves. The repository keeps its own shape and its own conventions |
| **not automatic architecture recovery.** Recovery describes what the code *is*; the model states what you *intend*, and the gap between them is the finding |
| **not a second source of truth.** The model is intent, the source is fact, and the map is checked against the tree every pass |
| **not all-or-nothing.** Unmapped is a first-class state with a number attached to it |

## Open

| question | recommendation |
|---|---|
| glob, regex or symbol in the map | all three; symbols matter where one file holds two components |
| what if a file belongs to two nodes | refuse it — overlap is how a map stops being checkable; split the file or the node |
| does an unmapped file block a task | no, but the task is asked to place what it touched: the map grows where the work goes |
| where does the map live | the repository it maps, beside its config — it is that repo's fact, not wecode's |

## Leans on

Murphy, Notkin & Sullivan, *Software Reflexion Models* — declare the model, declare the map,
compute convergence, divergence and absence; and the observation that a stated architecture
beats a recovered one because the architect can express the structure as needed. Lattix,
Sonargraph, Understand, Titan for the recovery half — clustering by inter-module dependency
to propose a decomposition. Parnas, for why the boundary is authored rather than discovered.
