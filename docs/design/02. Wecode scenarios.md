# Worked examples

Two, deliberately different in shape. The first is ordinary product work, where each
expectation has its own independent piece of work. The second is data work, where several
expectations are proven against one artefact.

## 1. Password reset

```
workspace  acme
  │
  └── project  storefront — the customer-facing shop
       │
       └── epic  account-recovery — a customer locked out can get back in
            │
            └── story  password-reset — a customer resets their password by email
                 │
                 └── requirement  a reset link authenticates exactly one password
                                  change by the address that asked for it
                      │
                      ├── acceptance_criteria  a reset link is emailed within 60s
                      │    ├── acceptance_test   request a reset, assert the mail
                      │    │                     arrives and contains a link      [live]
                      │    └── task              send the reset mail
                      │         ├── task_test    the mailer is called with the token
                      │         └── task_test    the token is signed and 30-minute expiry
                      │
                      ├── acceptance_criteria  the link sets a new password once
                      │    ├── acceptance_test   follow the link, set a password,
                      │    │                     log in with it                    [offline]
                      │    ├── task              build the reset form and handler
                      │    │    ├── task_test    a valid token renders the form
                      │    │    └── task_test    a good password is stored hashed
                      │    └── task              invalidate the token after use
                      │         └── task_test    a second use is rejected
                      │
                      ├── acceptance_criteria  an expired or forged link is refused
                      │    ├── acceptance_test   an expired token and a tampered
                      │    │                     token both refuse                [offline]
                      │    └── task              verify the token before rendering
                      │         └── task_test    expired, tampered and reused all fail
                      │
                      └── acceptance_criteria  reset requests are rate limited
                           ├── acceptance_test   the 6th request in an hour is
                           │                     refused                           [offline]
                           └── task              rate limit by email and by address
                                └── task_test    the 6th call in the window is refused
```

**Why this shape is easy.** Each expectation is an independent behaviour, so each has its
own work, and every task fulfils exactly one criteria. One criteria needed two tasks —
build the form, then invalidate the token — and that is ordinary rather than a strain.

**The requirement is a rule, not a paraphrase of the story.** *A reset link authenticates
exactly one password change by the address that asked for it* is a property with
consequences; the four criteria are its cases — who gets the link, how many times it
works, what happens when it is stale or forged, how often it may be asked for. Written as
a restatement of the story it would carry nothing the story did not already say, and the
layer would look redundant when it is not.

**Only one acceptance_test is `live`.** The other three can be proven in a checkout, so
most of the story completes unattended.

## 2. A generated database schema

```
workspace  acme
  │
  └── project  warehouse — the reporting warehouse
       │
       └── epic  bronze-layer — raw source data lands as queryable tables
            │
            └── story  bronze-from-extract — the twelve extract tables land as Iceberg
                 │
                 └── requirement  the twelve bronze tables exist in the catalog and
                                  mirror the source extract's columns and types
                      │
                      ├── acceptance_criteria  twelve tables exist in the catalog
                      │    ├── acceptance_test   the catalog lists 12 tables        [live]
                      │    └── task              apply the DDL to the catalog
                      │         └── task_test    applying twice is idempotent
                      │
                      ├── acceptance_criteria  columns and types match the extract
                      │    ├── acceptance_test   the verifier reports no mismatch   [live]
                      │    ├── task              generate the DDL from config
                      │    │    ├── task_test    12 statements come out of the yaml
                      │    │    └── task_test    the extract manifest parses
                      │    └── task              build the schema verifier
                      │         └── task_test    a seeded mismatch is detected and named
                      │
                      └── acceptance_criteria  every table carries the audit columns
                           ├── acceptance_test   the verifier reports audit columns
                           │                     on all 12                          [live]
                           └── task              add audit columns to the generator
                                └── task_test    every generated statement has them
```

**Why this shape is harder, and what the structure does about it.** The three expectations
are three assertions about **one artefact** — the generated DDL — so the work does not
split along them. Generating the DDL moves all three.

The structure survives it because a task's parent is its **intent**, not its effect:
*generate the DDL* was created because the columns criteria was red, so that is its parent.
That it also turned the other two green is measured by the tests, not by the edge.

**Every acceptance_test here is `live`.** So this story cannot complete unattended, and
that is visible at planning time rather than after a task has run and stopped for
credentials.

## 3. Where one criteria needs several tests

The first two examples are mostly one test per criteria, which makes the split between
them look like ceremony. It is not. A criteria is **one property**; a test is **one
mechanism for proving it**. When a property has to be proven three different ways, that is
one criteria and three tests — not three criteria.

```
story  password-storage — a customer's password cannot be read by anyone
  │
  └── requirement  a stored password is never recoverable, including by us
       │
       ├── acceptance_criteria  no stored password can be reversed to plaintext
       │    ├── acceptance_test  the stored value is argon2id with a per-user
       │    │                    salt and the tuned cost                      [live]
       │    ├── acceptance_test  two customers with the same password have
       │    │                    different stored values                      [offline]
       │    └── acceptance_test  the hash of a known password verifies, and a
       │                         near-miss does not                           [offline]
       │
       ├── acceptance_criteria  no password leaves the system in any form
       │    ├── acceptance_test  no API response body contains a hash or a
       │    │                    password field                               [offline]
       │    ├── acceptance_test  no logging call is reachable with a password
       │    │                    in its arguments                    [offline, static]
       │    ├── acceptance_test  a crash dump taken mid-login contains no
       │    │                    plaintext password                           [live]
       │    └── acceptance_test  the support console shows a masked value only  [manual]
       │
       └── acceptance_criteria  a password change invalidates every existing session
            ├── acceptance_test  after a change, an old session cookie is
            │                    refused                                      [offline]
            └── acceptance_test  a second device logged in before the change
                                 is signed out within 30s                     [live]
```

**Why none of these collapse.** Take the second criteria — *no password leaves the system
in any form*. Four tests: an API assertion, a static analysis of the call graph, a live
crash-dump inspection, and a human looking at a support screen. Four mechanisms, four
tiers, one property. Written as four criteria you would have fragmented one rule into four
and lost that they stand or fall together: if any one is red, passwords are leaking.

**And a criteria outlives its tests.** Swap argon2id for the next recommended algorithm and
all three tests under the first criteria change, while the criteria — *no stored password
can be reversed* — is untouched. That is the separation earning its place: the property is
stable, the mechanisms are not.

| criteria | tests | why several |
|---|---|---|
| cannot be reversed | 3 | the algorithm, the salting, and the round-trip are three distinct claims |
| never leaves the system | 4 | four exit routes, each needing a different mechanism to close |
| change invalidates sessions | 2 | one provable in a checkout, one needing a second live device |

## What the two examples show together

| | password reset | generated schema |
|---|---|---|
| expectations are | independent behaviours | assertions about one artefact |
| work splits along expectations | naturally | not at all |
| tasks per criteria | mostly one | one to two, all attacking the same one |
| acceptance_tests provable in a checkout | 3 of 4 | **none** |

**One task per criteria is the common case, not the rule.** A criteria may have several
tasks, and a criteria may end up green with none of its own because another task's work
reached it.

**A task_test never proves a requirement.** In both examples every task_test checks that
machinery works — a mailer is called, a generator generates, a verifier verifies. What
proves the requirement is always the acceptance_test, and in the second example all of
those needed a live system. Five green task_tests and an unproven requirement is a real
and easy state to be in.
