# Design and Stack

Where a change lands, and which technology may be there at all.

**On release 0.0.2.** Not started; drawn before implementation so it is not invented twice.

## Why

Two failures keep recurring, and neither is a bug in one place.

A task is dispatched into a scope somebody guessed. Tonight that cost six attempts on one
task and seven out-of-scope failures across the evening: the scope named files that held
none of the symbols the work needed, and nothing could say so before the agent started.

An agent reaches for a library nobody chose. Nothing in the record says *this project uses
`node:sqlite` and raw SQL*, so a dependency is one plausible suggestion away, and a
reviewer has to notice it in a diff.

Both are the same shape as the landed-story problem: the record knows what *should* be true
and the tree knows what *is*, and no one compares them. `design` is the missing statement
about structure; `stack` is the missing statement about technology.

## Two entities

| | design | stack claim |
|---|---|---|
| answers | where does this change land, and what does it promise | which technology may fill which role |
| belongs to | one story | the project, optionally narrowed to one component |
| lifetime | one story; stale when the base moves | until retired; outlives every story |
| authored by | the designer, proposing | you, approving |
| proved by | reading the tree — the index, not a test run | the evidence rule resolving at a built commit |

A design is a **document** whose claims are checkable. The prose is the point; the
structured fields exist so a gate can refuse what contradicts them.

## Where a library comes from

"A library we wrote" and "a library we import" are different facts. The difference selects
the evidence rule, and decides whether it needs a signature.

| origin | example | a stack claim? | evidence rule | signed by |
|---|---|---|---|---|
| `internal` | `@wecode/core`, `app/shared` | **no — it is a component** | already in the component map | gate |
| `published` | an internal package released outward | yes, once it has an external identity | `manifest:<name>` | you |
| `external` | `ink`, `react`, `psycopg` | yes | `manifest:ink@>=7 <8` | you |
| `builtin` | `node:sqlite`, `fs`, `node:test` | yes | `import:node:sqlite` | you, for a datastore-shaped one |
| `managed` | RDS Postgres, S3, SQS, Bedrock | yes — not a library, same shape | `iac:aws_db_instance.engine=postgres` | you |
| `vendored` | third-party source copied in | yes | `file:vendor/<path>` | you |

**An internal package is not duplicated as a stack row.** It is already a component with
modules; a second copy in another table is the defect, whatever format it is in.

**`builtin` is why manifests alone are not enough.** This repository's database is
`node:sqlite`. A dependency scan of this tree reports 13,041 installed packages and misses
that one — the single most important technology choice here has no package to find.

**The lockfile is excluded.** A scan of `student-success-p2-aut0` found `flask 3.1.3` in the
lock of a project with no Flask app: transitive, not chosen. Locks answer supply-chain
questions; declared manifests answer architectural ones.

## The stack claim

| column | holds |
|---|---|
| `role` | from a closed vocabulary in config, with a cardinality per role |
| `technology` | `postgres`, `react`, `node:sqlite`, or **`none`** |
| `origin` | `internal · published · external · builtin · managed · vendored` |
| `version_range` | the band inside which a bump needs no signature; empty for built-ins |
| `evidence_rule` | one of `manifest:` `import:` `iac:` `file:` |
| `scope` | the project, or one component address |
| `rationale`, `alternatives_rejected` | two lines each — the decision record, attached to the row it justifies |
| `provenance_sha` | the built tree the claim last resolved against |
| `state` | `proposed · approved · rejected · retired` |

`none` is a claim, not a blank. *No ORM here* and *no service layer* are decisions; a blank
row is an omission nobody can check.

### States

```
[*] → proposed → approved → retired → [*]
          ↓
       rejected → [*]
```

| transition | guard |
|---|---|
| `propose` | role is in the vocabulary · the evidence rule parses |
| `approve` | the role's cardinality has room · no conflicting approved claim in the same scope |
| `reject` | a reason, in your words |
| `retire` | no accepted design references it |

**A rejection is kept.** It is the answer to *may I add an HTTP client* for every later
agent, and deleting it invites the same proposal next week. A retired claim is kept for the
same reason: *what did we use before* is the question asked most.

**Resurrection is a new row, not a transition.** A retired or rejected claim that comes back
is proposed again, so the reason it returned is on the record beside the reason it left.

### The check

For each approved claim, at a built commit:

| outcome | meaning |
|---|---|
| **present** | the evidence rule resolved |
| **missing** | an approved technology is no longer there |
| **unclaimed** | a declared dependency exists that no claim covers |

`unclaimed` is the gate that matters: it is how a library nobody approved is caught the
moment it appears, rather than in review. The comparison runs against declared manifests,
imports and infrastructure — never a lockfile, never an installed tree.

## The design

| column | holds |
|---|---|
| `story_id` | its only parent |
| `statement` | the shape of the change, in words |
| `touches` | component addresses the change is expected to reach |
| `promises` | symbols to be added or changed, with kinds |
| `crosses` | ports: `!ui` `!cli` `!db` `!agent` |
| `uses` | the stack claims it relies on, including any it is *asking* for |
| `verdict` | convergence / divergence / absence at accept time |
| `provenance_sha` | the tree it was read against |
| `state` | `drafted · accepted · superseded · dropped` |

### States

```
[*] → drafted → accepted → superseded → [*]
         ↓          ↓
      dropped    dropped → [*]
```

| transition | guard |
|---|---|
| `accept` | the verdict holds no divergence · every component address exists in the map · every promise resolves in the index · **every claim it uses is approved** |
| `supersede` | a newer design on this story has been accepted |
| `drop` | the story was dropped |

**Stale is derived, never stored.** A design is stale when its `provenance_sha` is no longer
an ancestor of the base, or when a component it touches has changed since. Storing it would
be a flag somebody must remember to set; computing it makes it level-triggered, the same
reason `behind` and `landed` are asked of git rather than kept in a column.

**A design asking for a new library waits without a new state.** `accept` requires its
claims approved, so a document that needs Redis simply cannot be accepted until the Redis
claim is. There is no `blocked`.

## A blank project declares its stack first

A new project's canvas is the role vocabulary itself: one row per role before the first
story, each either a technology or an explicit `none`. That makes *we deliberately have no
backend* a fact on the record, and gives the first design something to reference.

## What needs your signature

| level | change | decided by | because |
|---|---|---|---|
| 0 | code inside an approved scope; test wording | gate | redone in minutes |
| 1 | a new module inside an existing component; a design asking for nothing new | gate | visible in the diff |
| 2 | a version bump beyond the declared range | gate, inside an allowlist | recorded, not signed — otherwise you sign dependency-bot noise |
| 3 | **a new external library, or a role filled for the first time** | **you** | a dependency is a standing commitment, not a line of code |
| 4 | **a technology swap; a new component, port, or permitted boundary crossing** | **you** | the boundary *is* the decision |
| 5 | publish, push to a public remote, rewrite history, drop a branch, change a verdict | **you** | one-way doors |

Three properties of an approval, so it cannot be inherited by accident:

| | |
|---|---|
| an approval names the claim it approved | signing `react >=19 <20` does not sign `react >=20`; editing the range invalidates the approval |
| an approval is its own row | one claim carries several over its life, each with who and when |
| an approval expires with staleness | it carries the provenance it was given against, so *approved three swaps ago* cannot be cited as current |

**The design is not what you sign.** What reaches you is the claim a design references — the
dependency, the swap, the boundary. A design that asks for nothing above level 2 is accepted
by the gate.

## Prior art — the four levels already have conventions

The structure you want — external container, external library, package, module — is not
missing. It exists four times, each level owned by a different tool, which is why it looks
like nobody bothered: no one convention spans all four.

| level | the convention | text form | who runs it in anger |
|---|---|---|---|
| **external container** | **C4** — *software system*, marked external | **Structurizr DSL** `workspace.dsl`: `softwareSystem "Stripe" { tags "External" }` | the C4 author's own reference implementation; architecture-as-code with version control and diagram generation |
| **external library** | **SBOM** — SPDX, CycloneDX | JSON/XML per dependency, plus the declared manifest | the supply-chain world, now regulated |
| **package** | the **project graph** | `nx graph`, Turborepo, Bazel targets; C4 *container* | every large monorepo |
| **module** | the **symbol index** | SCIP / LSIF; the module graph from dependency-cruiser or madge | code intelligence, cross-repo navigation |

And the rules over them are equally well trodden:

| tool | asserts |
|---|---|
| **ArchUnit** (Java), **ArchUnitTS** | layer rules as ordinary tests, run in CI |
| **dependency-cruiser** | forbidden edges, cycles, orphan modules, *is this shared enough* |
| **eslint-plugin-boundaries**, **Nx tags** | boundaries at build time, per-package tags |

> *dependency-cruiser and madge build a real module graph, ArchUnit and NetArchTest assert
> layer rules against compiled bytecode, eslint-plugin-boundaries and Nx/Bazel enforce
> boundaries at build time.*

The shared principle is the one this page already rests on: **architectural intent is
executable, so a violation fails the build instead of silently accumulating.**

### What is genuinely missing

| gap | why it matters here |
|---|---|
| **no convention spans the four levels** | C4 stops above the module; SCIP stops below the package; SBOM only knows external libraries. A question like *does this module reach that external system* crosses three tools |
| **the map is declared, never checked against the tree** | Structurizr's model is authored by hand and drifts; that is precisely what Reflexion models were invented to catch, and what `components.yaml` plus the cover-the-tree test does here |
| **external libraries and internal structure are separate records** | the stack claim table above joins them: one row per role, whether it is filled by `internal`, `external` or `managed` |

So wecode is not inventing a level — it is joining four that already exist:

```
external container  ← C4 / Structurizr vocabulary
external library    ← the stack claim, evidence rule `manifest:` / `import:` / `iac:`
package             ← components.yaml, checked by components-cover-the-tree
module              ← the explorer's index (tree-sitter), one row per module
```

**Take the vocabulary, not the tooling.** `softwareSystem` / `container` / `component` are
the words the architecture community already reads, and using them costs nothing; running
Structurizr would mean a second model to keep in step with this one.

## Invariants

| | |
|---|---|
| a story in `ready` or beyond has exactly one accepted design, and that design is not stale |
| every task's scope contains the symbols its design promised for it |
| every component address a design names exists in the component map, and no pair it names crosses a forbidden dependency |
| every declared dependency in the tree is covered by an approved claim |
| no approved claim is missing from the tree without the doctor saying so |
| a superseded design and a rejected claim are never deleted |

## What this is not

| | |
|---|---|
| **not a schema for the prose.** The statement is a document; only the fields around it are structured |
| **not a second component map.** Internal packages stay in `components.yaml` |
| **not a supply-chain tool.** Licences and vulnerabilities are a nightly scan's job, on the installed tree, not this record's |
| **not an audit.** The gates run on the diff — a change is judged when it is made, not swept for afterwards |

## Open

| question | recommendation |
|---|---|
| the role vocabulary | start with `ui · transport · service · domain · orm · database · cache · queue · iac · test · build · observability`; add a role only when a claim will not fit one |
| does level 2 auto-approve inside an allowlist | yes — patch and minor of already-approved technologies |
| is the scope check binding or advisory | binding: a refusal before the work beats three burnt attempts |

## Leans on

Parnas, *On the Criteria To Be Used in Decomposing Systems into Modules* — a boundary is a
decision, so it is authored rather than discovered. Murphy, Notkin & Sullivan, *Software
Reflexion Models* — declare a high-level model, declare the map to source, compute
convergence, divergence and absence; the stack check is that triple on the dependency axis.
Fowler — architecture is the set of decisions expensive to reverse, which is where the
signatures belong. One-way and two-way doors, for the levels themselves.
